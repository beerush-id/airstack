# Aria Kits

Building accessible web applications is difficult. Developers often face a frustrating trade-off: adopt heavyweight component libraries that dictate your markup, styles, and bundle size, or manually wire dozens of WAI-ARIA attributes, manage focus states, and polyfill keyboard interactions by hand.

**Aria Kits** (`@airlib/aria`) eliminates this trade-off. It provides headless behavioral state machines that manage accessibility semantics, keyboard navigation, and composite coordination—without imposing any CSS, HTML markup structure, or DOM wrappers.

## Live Examples

Some roles cost a week before they feel right — the searchable picker, the folder tree, the calendar popup, the modal. Four of them are live below. Try them first; the markup and styles are the ones written on this page, so nothing here is a mock-up or a screenshot.

:::interactive[City picker]{standalone}
```tsx
import { aria } from '@airlib/aria';
import { derived, For, setup, shadowPortal } from '@airlib/react';
import type { ComponentProps } from 'react';

const cityMap: Record<string, string> = {
  ams: 'Amsterdam',
  ber: 'Berlin',
  cop: 'Copenhagen',
  dnb: 'Dublin',
  vil: 'Vilnius',
};
const cities = Object.entries(cityMap);

type DemoCityProps = ComponentProps<'div'> & {
  value?: string | string[] | null;
  query?: string;
  open?: boolean;
  multiple?: boolean;
  disabled?: boolean;
  required?: boolean;
};

const DemoCity = setup<DemoCityProps>((props) => {
  const combobox = aria('combobox', props, cityMap);

  const matches = derived(() => {
    const query = combobox.query.trim().toLowerCase();
    return cities.filter(([key, city]) => key.includes(query) || city.toLowerCase().includes(query));
  });

  return () => (
    <div ref={combobox.ref} {...combobox.restProps(['children'])} className="demo-combobox">
      <DemoCityInput label="City" />
      <DemoCityPanel>
        <For each={() => matches.value}>
          {([key, city]) => <DemoCityOption value={key}>{city}</DemoCityOption>}
        </For>
        {matches.value.length === 0 ? <div className="demo-combobox-empty">No city matches that.</div> : null}
      </DemoCityPanel>
    </div>
  );
}, 'DemoCity');

type DemoCityInputProps = ComponentProps<'input'> & {
  label?: string;
};

const DemoCityInput = setup<DemoCityInputProps>((props) => {
  const input = aria<HTMLInputElement>('combobox-input', props);

  return () => (
    <span className="demo-combobox-field">
      <input
        ref={input.ref}
        {...input.restProps(['children', 'label'])}
        aria-label={props.label}
        placeholder="Type to filter"
        className="demo-combobox-input"
      />
      <span className="demo-combobox-caret" aria-hidden="true" />
    </span>
  );
}, 'DemoCityInput');

const DemoCityPanel = setup<ComponentProps<'div'>>((props) => {
  const panel = aria<HTMLElement>('combobox-panel', props);
  const shadow = shadowPortal(() => true);

  return () =>
    shadow(
      <div ref={panel.ref} {...panel.restProps(['children'])} className="demo-combobox-panel">
        {props.children}
      </div>
    );
}, 'DemoCityPanel');

type DemoCityOptionProps = ComponentProps<'div'> & {
  value: string;
  disabled?: boolean;
};

const DemoCityOption = setup<DemoCityOptionProps>((props) => {
  const option = aria('option', props);

  return () => (
    <div ref={option.ref} {...option.restProps(['children'])} className="demo-combobox-option">
      {props.children}
    </div>
  );
}, 'DemoCityOption');
```

## The Mental Model

Aria Kits operates on a simple principle: **Behavior without presentation**.

Instead of rendering DOM elements, an ARIA controller acts as a reactive bridge between your component's state and the browser DOM through two primary touchpoints:

1. **`attributes`**: A reactive getter returning the compiled dictionary of HTML and ARIA attributes (`role`, `aria-*`, `tabindex`, `disabled`). Whenever underlying reactive state changes, attributes recompile automatically.
2. **`ref`**: A lifecycle callback attached to the DOM node. It registers keyboard and pointer listeners, synchronizes DOM properties, and handles cleanup on unmount.

Every demo above is those two touchpoints. The controllers own no element of their own — they write onto the elements you render.

Because the controller only manages attributes and events, you retain 100% control over your markup, CSS, and component structure.

## Component Integration

In AirLib, components built with `setup` receive reactive `props`. When passed directly into the `aria()` factory, the controller binds to that existing reactive proxy—eliminating glue code, change-detection boilerplate, and intermediate state management.

:::code-group

```tsx [React]
import { aria } from '@airlib/aria';
import { setup } from '@airlib/react';
import type { ComponentProps } from 'react';

export type ActionButtonProps = ComponentProps<'button'> & {
  disabled?: boolean;
};

export const ActionButton = setup<ActionButtonProps>((props) => {
  const button = aria('button', props);
  const restProps = props.$omit([...button.ownKeys, 'disabled', 'children']);

  return () => (
    <button ref={button.ref} {...restProps} {...button.attributes}>
      {props.children}
    </button>
  );
});
```

```tsx [SolidJS]
import { aria } from '@airlib/aria';

});
```

## Safe Prop Forwarding with ownKeys

When building reusable components that forward consumer props to underlying DOM elements, two pitfalls must be avoided:

1. **Attribute Collisions**: User props can inadvertently collide with or shadow attributes compiled by the ARIA controller.
2. **Prop Leakage**: Component input props (such as `disabled`, `children`, `className`) should not leak onto the DOM as raw HTML attributes.

`Aria.prototype.ownKeys` exposes the exact array of attribute and listener names currently compiled on `controller.attributes`. Passing `controller.ownKeys` along with component-specific keys to `props.$omit(...)` produces a clean `restProps` object:

```tsx
const restProps = props.$omit([...controller.ownKeys, 'children', ...controlledKeys]);
```

Spreading `{...restProps}` before `{...controller.attributes}` ensures that consumer props (such as custom `onClick`, `title`, or `data-*` attributes) safely reach the DOM without overriding ARIA contracts.

## Native vs Custom Element Contracts

A primary goal of AirLib ARIA is to avoid redundant DOM work while ensuring complete accessibility:

- **Native Elements** (`native: true`, default): When attached to native HTML elements (`<button>`, `<input>`), the controller avoids setting redundant ARIA attributes (`role="button"`) and lets the browser handle native keyboard events and form submission.
- **Custom Elements** (`native: false`): When building buttons or toggles from non-interactive tags (`<div>`, `<span>`), the controller polyfills the missing browser capabilities by injecting `role`, managing `tabindex` focusability, and handling `Enter` and `Space` keyboard activation.
