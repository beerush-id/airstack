# AirLib Headless Toolbar

An editor bar packs undo, redo, formatting toggles, and alignment options into one strip. Assistive technology announces it as a loose pile of controls with no name and no relationship, and the arrow keys do not travel along it. Nesting a radio group or a toggle group inside makes that second half worse: each group claims the arrows for itself, so they stop at the group boundary. **AirLib Headless Toolbar** (`aria('toolbar')`) names the strip for assistive technology and carries arrow-key travel across everything inside it — nested groups keep their own role and their own selection state.

```tsx
const toolbar = aria('toolbar', props);

<div ref={toolbar.ref} {...toolbar.props} />
```

```tsx
import { aria } from '@airlib/aria';
import { setup } from '@airlib/react';
import type { ComponentProps } from 'react';

type DemoToolbarProps = ComponentProps<'div'> & {
  label?: string;
  orientation?: 'horizontal' | 'vertical';
  disabled?: boolean;
};

const DemoToolbar = setup<DemoToolbarProps>((props) => {
  const toolbar = aria('toolbar', props);

  return () => (
    <div ref={toolbar.ref} {...toolbar.props} className="demo-toolbar">
      {props.children}
    </div>
  );
}, 'DemoToolbar');

type DemoToolbarButtonProps = ComponentProps<'button'> & {
  disabled?: boolean;
};

const DemoToolbarButton = setup<DemoToolbarButtonProps>((props) => {
  const button = aria('button', props);

  return () => (
    <button ref={button.ref} {...button.restProps(['children'])} className="demo-toolbar-button">
      {props.children}
    </button>
  );
}, 'DemoToolbarButton');

type DemoToolbarToggleProps = ComponentProps<'button'> & {
  pressed?: boolean;
  disabled?: boolean;
};

const DemoToolbarToggle = setup<DemoToolbarToggleProps>((props) => {
  const toggle = aria('toggle', props);

  return () => (
    <button ref={toggle.ref} {...toggle.restProps(['children'])} className="demo-toolbar-toggle">
      {props.children}
    </button>
  );
}, 'DemoToolbarToggle');
```

## Toolbar

Stateless focus container that compiles `role="toolbar"` and owns arrow-key travel across its descendants.

```ts
aria<E extends BaseElement = HTMLElement>(
  role: 'toolbar',
  props?: ToolbarProps
): ToolbarAria<E>
```

### Usage

:::code-group

```tsx [React]
import { aria } from '@airlib/aria';
import { setup } from '@airlib/react';
import type { ComponentProps } from 'react';

type ToolbarProps = ComponentProps<'div'> & {
  label?: string;
  orientation?: 'horizontal' | 'vertical';
  disabled?: boolean;
};

const Toolbar = setup<ToolbarProps>((props) => {
  const toolbar = aria('toolbar', props);

  return () => (
    <div ref={toolbar.ref} {...toolbar.props}>
      {props.children}
    </div>
  );
});
```

```tsx [SolidJS]
import { aria } from '@airlib/aria';
import { setup } from '@airlib/solid';
import type { ComponentProps } from 'solid-js';

type ToolbarProps = ComponentProps<'div'> & {
  label?: string;
  orientation?: 'horizontal' | 'vertical';
  disabled?: boolean;
};

const Toolbar = setup<ToolbarProps>((props) => {
  const toolbar = aria('toolbar', props);

  return (
    <div ref={toolbar.ref} {...toolbar.props}>
      {props.children}
    </div>
  );
});
```

:::

### Parameters

- `props.label` *(string, optional)*: Accessible name for the toolbar, applied via `aria-label`.
- `props.orientation` *('horizontal' | 'vertical', optional, default `'horizontal'`)*: Axis the arrow keys travel, compiled to `aria-orientation`.
- `props.disabled` *(boolean, optional)*: Locks the toolbar out of keyboard roving and announces `aria-disabled`.

### How it behaves

- Compiles `role="toolbar"`, an explicit `aria-disabled` baseline, and `aria-orientation` on both axes.
- Arrow keys move focus across every enabled control in the bar and wrap at both ends, never escaping to elements outside it.
- Arrows move focus only. Activation stays with the control, on its own `click`, `Enter`, or `Space`.
- Controls you add or remove later are picked up on the next keystroke.
- A radio group or toggle group inside the toolbar keeps working as itself — same role, same label, same value — while the toolbar carries the arrows across it.
- Pressed and checked state stays on each control; the toolbar holds none.
- A disabled toolbar claims no keystroke at all.

:::tip[No Toolbar Item Role]
WAI-ARIA defines no toolbar item role, so there is no `Toolbar.Item` to reach for. Any focusable control you place inside — button, toggle, checkbox, link — participates in roving by being there.
:::

## Controls

Toolbar members are the ordinary role controllers: [`aria('button')`](/docs/aria/button), [`aria('toggle')`](/docs/aria/toggle), [`aria('checkbox')`](/docs/aria/checkbox), [`aria('link')`](/docs/aria/link). Each keeps its own props, projections, and activation keys. Nested groups such as [`aria('radio-group')`](/docs/aria/radio-group) and [`aria('toggle-group')`](/docs/aria/toggle-group) keep coordinating their own value while the toolbar owns the arrows.

## Keyboard Navigation

- **ArrowRight / ArrowLeft**: Moves focus across controls in a horizontal toolbar, wrapping at both ends.
- **ArrowDown / ArrowUp**: Moves focus across controls in a vertical toolbar, wrapping at both ends.
- **Home / End**: Moves focus to the first or last enabled control.
- **Space / Enter**: Left to the focused control, which activates itself.
- **Tab**: Left to the browser, moving focus to the next interactive element on the page.

## What you get

- **Arrow travel across the whole bar.** One press moves one control, straight through any nested group.
- **Groups stay groups.** A radio group or toggle group inside a toolbar keeps its role, its label, and its selection behavior.
- **Nothing to configure.** No value, no selection timing, no list of members.
- **Controls come and go freely.** Add or remove a button without wiring it up.
- **Zero markup lock-in.** Native controls or custom hosts; the toolbar only moves focus.
